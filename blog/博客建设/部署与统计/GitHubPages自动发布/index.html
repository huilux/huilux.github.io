用 GitHub Actions 把 Astro 博客发布到 GitHub Pages

把 Astro 静态博客发布到 GitHub Pages 的完整教程：私有源码仓库 + 公开 Pages 仓库的双仓库架构、write deploy key、自动构建 workflow 与上线验证。

内容时效

本文最后维护于20 天前，部分技术细节可能已经变化，请结合当前版本和官方文档核对。

这篇文章记录我把一个 Astro 静态博客发布到 GitHub Pages 的完整过程。核心诉求有两点：

  1. 博客是纯静态站点，希望用 GitHub Pages 免费托管，域名就是 https://<用户名>.github.io/；
  2. 源码仓库保持私有——不想把 Astro 源码、草稿和构建脚本暴露出去，只让最终站点公开。

这两点合在一起，第一次做的人会踩一个关键坑：GitHub 免费版的 Pages 只对公开仓库开放。 私有仓库要用 Pages，得购买 Pro / Team / Enterprise 套餐。所以对不想付费的人来说，「仓库私有」和「Pages 免费」二者不可兼得——除非换一种架构。

核心思路：双仓库

解决方案是把「源码」和「产物」拆到两个仓库：

仓库可见性内容作用
<用户名>/<博客名>私有Astro 源码、草稿、构建脚本唯一事实来源，日常开发在这里
<用户名>/<用户名>.github.io公开每次构建生成的 dist/ 静态文件由 GitHub Pages 托管

每次推送到源码仓库的 master 分支，GitHub Actions 就在云端完成「安装依赖 → 质量检查 → 构建」，再把 dist/ 用 write deploy key 推到公开的 Pages 仓库。于是：

  • 源码始终私有；
  • 公开仓库里只有构建产物，没有源码；
  • 发布是自动的，本地只需要 git push。
私有源码仓库 ──push──▶ GitHub Actions ──dist/──▶ 公开 Pages 仓库 ──▶ https://<用户名>.github.io/

为什么 Pages 仓库要叫 <用户名>.github.io？因为 GitHub 会把这种「用户站点」部署在根路径 https://<用户名>.github.io/。此时 Astro 不需要设置 base，所有站内链接都是绝对根路径，最简单。如果部署成某个普通仓库的「项目站点」，站点会出现在 /仓库名/ 子路径下，还得给 Astro 配 base 并处理所有内部链接，麻烦得多。

（本例实际的账号是 huilux：源码仓库 huilux/huilux-astro，Pages 仓库 huilux/huilux.github.io。）

前置准备

  • 一个 npm run verify 能全绿的 Astro 项目。我把质量门禁放进 CI，保证每次发布前都先过一遍格式检查、内容审计、类型检查和生产构建；
  • 本地安装 gh（GitHub 官方 CLI）并登录：gh auth login；
  • 想清楚生产域名。Astro 的 site 由 SITE_URL 环境变量注入，会写进 canonical、RSS、Sitemap 和结构化数据，构建时务必带上。

步骤一：创建两个仓库

源码仓库用 gh repo create 一步完成「建仓 + 设远程 + 推送」：

gh repo create <你的用户名>/<博客名> --private --source . --remote origin --push
  • --source .：以当前目录为仓库内容；
  • --remote origin：自动把本地远程指到新仓库；
  • --push：推送当前分支（本地是 master）。

再推送开发分支，并把默认分支设为 master：

git push origin dev
gh repo edit <你的用户名>/<博客名> --default-branch master

公开 Pages 仓库单独创建，加一个 README 让 main 分支先存在：

gh repo create <你的用户名>/<你的用户名>.github.io --public --add-readme

步骤二：配置 write deploy key

跨仓库发布的关键问题：源码仓库的 GITHUB_TOKEN 只在它自己的仓库里有权限，推不动别人的仓库。标准做法是用 deploy key：

  1. 生成一对无口令的 ed25519 密钥；
  2. 把公钥作为「写权限 deploy key」加到公开 Pages 仓库；
  3. 把私钥作为 secret PAGES_DEPLOY_KEY 存进私有源码仓库，供 workflow 使用。

这样私钥只存在于私有仓库的 secret 中，公钥只存在于公开仓库的 deploy key 列表里，二者分离、权限面最小——CI 机器对公开仓库的能力只有「写 Pages 仓库」这一种。

# 1. 生成密钥对
ssh-keygen -t ed25519 -C "gh-pages-deploy" -N "" -f /tmp/pages-deploy-key

# 2. 公钥加为公开仓库的写权限 deploy key
gh repo deploy-key add /tmp/pages-deploy-key.pub \
  -R <你的用户名>/<你的用户名>.github.io \
  -t "pages-deploy" --allow-write

# 3. 私钥存为私有仓库的 Actions secret
gh secret set PAGES_DEPLOY_KEY -R <你的用户名>/<博客名> < /tmp/pages-deploy-key

# 4. 清理本地临时密钥
rm -f /tmp/pages-deploy-key /tmp/pages-deploy-key.pub

添加成功后 GitHub 会给仓库所有者发一封「新 SSH key 已添加」的邮件——这是预期行为，不是安全告警。

步骤三：启用 GitHub Pages

对 <用户名>.github.io 这种用户站点，GitHub 会在检测到仓库名时自动开启 Pages 并指向默认分支。也可以显式用 API 配置为「从 main 分支的根目录发布」：

gh api --method POST repos/<你的用户名>/<你的用户名>.github.io/pages \
  -f 'source[branch]=main' -f 'source[path]=/'

如果提示 GitHub Pages is already enabled（HTTP 409），说明已经自动开启，忽略即可。也可以在网页端 Settings → Pages → Build and deployment → Deploy from a branch 里手动选择 main + / (root)。

步骤四：编写 workflow

在源码仓库新增 .github/workflows/deploy.yml：

name: Deploy to GitHub Pages

on:
  push:
    branches: [master]
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: pages
  cancel-in-progress: true

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node
        uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: npm

      - name: Install dependencies
        run: npm ci

      - name: Build (quality gates)
        run: npm run verify
        env:
          SITE_URL: https://<你的用户名>.github.io

      - name: Deploy to GitHub Pages
        uses: peaceiris/actions-gh-pages@v4
        with:
          deploy_key: ${{ secrets.PAGES_DEPLOY_KEY }}
          external_repository: <你的用户名>/<你的用户名>.github.io
          publish_branch: main
          publish_dir: ./dist
          force_orphan: true

逐块解释：

  • on.push.branches: [master]：只在推送 master 时发布；开发分支推送不会触发。想手动触发就点 workflow 的 Run workflow（对应 workflow_dispatch）。
  • permissions: contents: read：整个 job 只读本仓库。发布用的是 deploy key，不需要多余的 token 权限，遵循最小权限原则。
  • concurrency：同一时间只跑一个发布 job，避免连续推送时互相覆盖。
  • actions/setup-node + cache: npm：固定 Node 版本并缓存依赖，加速安装。
  • npm ci：按 package-lock.json 精确安装，保证云端与本地依赖完全一致（比 npm install 更严格、可复现）。
  • npm run verify + SITE_URL：把生产 origin 注入构建，同时把「格式检查 → 内容审计 → Astro 类型检查 → 生产构建」整条质量门禁放进 CI。任何一步不过，就不发布。
  • peaceiris/actions-gh-pages：跨仓库部署的事实标准。external_repository 指向目标仓库，deploy_key 提供写权限，publish_dir 是 dist/，publish_branch 推到 main。force_orphan: true 让 Pages 仓库只保留干净的一次性提交历史，不会有陈旧文件残留。

步骤五：推送，自动发布

git push origin master

查看 CI 状态：

gh run list
gh run watch

首次成功后，核对线上：

# 首页 / 文章 / 旧链接
curl -sI https://<你的用户名>.github.io/
# RSS 与 Sitemap 的 origin 是否正确
curl -s https://<你的用户名>.github.io/rss.xml
# canonical 不是 localhost
curl -s https://<你的用户名>.github.io/blog/... | grep canonical

我这次核对的结果：

  • 首页、文章页、RSS、Sitemap 均返回 200；
  • canonical / RSS / Sitemap 的 origin 都是 https://huilux.github.io，而不是本地 localhost:4321；
  • 从旧博客保留的 /posts/... 兼容链接能正常打开；
  • 访问不存在的路径会返回自定义 404 页（状态码 404，但展示的是站内 404 页面）。

遇到的坑与注意点

推送大仓库失败 unable to rewind rpc post data

历史内容较多时，首次推送的 pack 可能超过默认的 HTTP 缓冲，报 http.postBuffer 相关错误。调大缓冲后重试即可：

git config http.postBuffer 524288000
git push -u origin master

用户站点的 Pages 会自动开启

<用户名>.github.io 的仓库建好就自动被 GitHub 当作站点，不用再手动重复开启。

/posts/ 旧链接不是 HTTP 301

静态托管平台上，Astro.redirect 会输出带 canonical 和立即刷新的 HTML 兼容页，但不会真的返回 301 状态码。对 SEO 要求严格的场景，需要把重定向规则配置到平台层。

草稿不会泄漏

draft: true 的文章只在本机开发时可见，生产构建会过滤掉，所以私有仓库里的草稿不会被发布到公开站点。

日常使用

之后写文章只需走老流程：内容写好 → 本地 npm run verify → git push origin master，剩下全部交给 GitHub Actions。改动任何环节（域名、品牌文案）时，记得同步更新 workflow 里的 SITE_URL。
